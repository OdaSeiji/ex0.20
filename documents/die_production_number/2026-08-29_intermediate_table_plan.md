# 型番-品番「1対多化」検討 まとめ

- 作成日: 2026-08-29(検討開始)、2026-08-30 結論に基づき全面改訂
- 対象システム: ex0.20 (`C:\xampp\htdocs\ex0.20`)
- ステータス: **中間テーブル方式は不採用。対応は第2弾(プレス指示移植)側の「計画長さ」列追加のみで足りる、という結論**

## 1. 結論(2026-08-30)

「1つの型番で複数の品番を生産したい」という要望の実態は、**製品の断面形状(=金型)は変えず、押出後に切る長さだけが
違うものを扱いたい**、というものだった。

- `m_dies.production_number_id`(型番→品番の単一FK)は**変更不要**。中間テーブルは作らない。
- 長さ違いごとに新しい品番(図面)コードを発番する現行の運用(`-20K`/`-30K`のような品番、後述)は、正式な図面を伴わない
  「その場しのぎ」の登録であり、これを助長する設計(型番に複数品番を正式に紐づけられるようにする)はすべきでない。
- 本当に必要なのは、**プレス指示(計画)時点で「今回は何mで作るか」を記録できる場所**。実績側は`t_press.first_actual_length`
  で既に対応済み。計画側は現状ex0.20に画面自体が無い(プレス指示はex0.11にしか無く、第2弾で移植予定)。
- したがって対応は、**第2弾でプレス指示画面をex0.20へ移植する際に「計画長さ」列を持たせる**、それだけでよい。
  型番マスタ・品番マスタのスキーマ変更は不要。

**今朝(2026-08-30)ローカル環境で作成した中間テーブル`t_die_production_numbers`はDROP済み。**
`m_dies.production_number_id`自体は一度も変更していないため、DROPのみで完全に元の状態に戻っている。
本番PCへは元々このSQLを未実行だったため、対応不要。

## 2. 検討の経緯(記録として残す)

1. 当初、「型番:品番 = 1:1」を「1:多」に拡張する方針で、中間テーブル`t_die_production_numbers`
   (die_id, production_number_id, is_primary)を設計・ローカルDBに作成し、`m_dies.production_number_id`から
   1234件をバックフィルした(2026-08-29)。
2. 2026-08-30の議論で、「品番が複数になる」とは実際には「同じ形状のまま長さだけ違う」ことだと判明。
   `m_production_numbers`の列構成(`circumscribed_circle`・`cross_section_area`・`specific_weight`等の形状系属性と
   `production_length`・`production_number`の長さ系属性が同居)がこれを裏付けた。
3. さらに議論を進め、「そもそも長さ違いの品番(図面)自体が正式には存在しない」という業務上の実態が判明。
4. 実データで検証したところ、次の事実が見つかった:
   - 品番コードに`-20K`/`-30K`のような長さを示す接尾辞を付けて、同じ形状の品番が複数登録されている実例が
     `m_production_numbers`に多数存在する(例: `C2Q12A-AD367-20K`と`C2Q12A-AD367-30K`)。
   - `m_dies.production_number_id`が単一FKしか持てないため、同じ物理金型を3m版でも登録するために、
     `die_number`に`-ZZZ`を付けた**複製の金型マスタ行**を作る、という運用回避策が取られていた
     (例: `CQ12T3L-V01B`(2m版・die_id 192)と`CQ12T3L-V01B-ZZZ`(3m版・die_id 746)は本来同一の金型)。
   - この`-ZZZ`複製金型には実際のプレス実績が多数あり(die_id 746で9件、863で17件など、2024〜2026年にかけて継続的に発生)、
     運用ニーズ自体は確かに実在し、現在進行形で使われていることを確認した。
   - ただし品番コード側(`-20K`/`-30K`)は正式な図面を伴わない、システム上の都合で作られたものであり、
     これをマスタとして正式に「型番の複数品番」として管理・拡充していく設計は妥当ではない、と判断した。
5. 結論として、型番・品番マスタの構造は変えず、「計画時にその回の長さを記録する」という運用側の仕組みで
   対応する方針に切り替えた(1章参照)。

## 3. 今後の対応(第2弾に統合)

- 元の「第2弾: プレス指示・プレス計画のex0.20移植」計画([[project_die_pn_1tomany]]参照)に、以下を追加する:
  - プレス指示(`t_press_directive`相当、ex0.11の`MakingPressDirectiveV11.html`を移植)に**計画長さ**の列を追加する。
  - デフォルト値は紐づく品番の`production_length`を提案しつつ、その回だけ違う長さを指定できるようにする。
- `t_press`側は`first_actual_length`が既にあるため変更不要。
- 型番登録(`die_register.html`)への複数品番選択UIは**不要になった**(当初5章で予定していたが削除)。
- 中間テーブル・型番マスタ・品番マスタのスキーマ変更は行わない。

## 4. 参考: 見つかった技術的負債(今回の対応スコープ外)

以下は今回の意思決定には使うが、対応自体は本検討のスコープ外とする、既知の問題として記録しておく。

- `die_number`に`-ZZZ`を付けた複製金型が複数存在する(少なくとも`CQ12T3L-V01B`/`CQ20T3-V01B`/`CQ25T3-V01B`/
  `CQS20T-V01D`/`CQS25T-V01D`/`CYV15K-V01D`系列で確認、他にもある可能性)。いずれも本来は同一物理金型。
- 対応する品番側にも`-20K`/`-30K`のような長さ接尾辞違いの重複コードが存在する。
- 3章の対応(プレス指示への計画長さ列追加)が実現すれば、これらの複製金型・複製品番は将来的に運用上不要になる
  はずだが、既存の実績データ(過去のプレス記録)が紐づいているため、統合(データ移行)は別途慎重な検討が必要。
  今回は現状維持とし、触らない。
